# WebGPU Mandelbrot 交互探索器

单文件、零依赖、无引擎。UI 与架构参考 [Noniv/web-ocean](https://github.com/Noniv/web-ocean)（自包含 WebGPU 页面 + HUD + 玻璃设置面板）。

## 运行

直接双击打开 mandelbrot.html

## 操作

|---|---|
| 拖拽 | 平移 |


| 参数 | 含义 |

## 交互不闪屏

闪屏有三处独立来源，现在都堵住了。

**1. 参考轨道不能钉在视图中心。** 这是最主要的一个。扰动法要求参考轨道 `R_n` 本身有界；视图中心绝大多数时候在集合**外面**，轨道三十来步就逃逸，`|R|` 一路平方出去，GPU 上每个像素都继承这个逃逸——整屏塌成一片平滑渐变。拖过边界时画面就是这样一帧塌掉，而且只要参考轨道不重建就一直塌着。

现在改为在视图上撒 5×5 网格，挑一个**跑满迭代预算**的点当参考，同分时取离中心最近的（`refOffset` 越小越准）。网格里一个都没活下来，说明这一屏全是外部、根本不需要长轨道，于是退到"参考点 = 原点"，等价于不做扰动的普通迭代——它在浅缩放是精确的，而且永远不会点亮"内部"。

**2. 交互时降的是分辨率，不是迭代数。** 迭代预算决定"逃逸/内部"的分界落在哪里，一降就会让边界细丝变细、辉光变暗，抬手再弹回来——拖拽开始和结束各闪一下。所以现在渲染到一张离屏纹理上、按 55% 尺寸画、再线性放大铺满画布；画布本身尺寸不变，绘制缓冲不会被清空，颜色也完全不变，代价只是手势期间略糊。

**3. 参考轨道缓冲一次分配到位。** 旧实现按需 `destroy()` 再重建 storage buffer 和 bind group，可能拆掉 GPU 还在读的东西。现在固定 2048 槽（`maxIter` 上限 2000、轨道按 1.35 倍建，够用），bind group 建一次不再动。

另外：画布 `resize` 只在窗口尺寸真正变化时才做（每帧读 `clientWidth` 会强制 layout，而且重配 context 正好卡在 `getCurrentTexture()` 中间）；窗口 `resize` 做了防抖。

> 预设切换时画面会短暂全黑——那不是 bug。切预设是位置/缩放的插值过渡，路径会从集合内部穿过去，而内部本来就是黑的。按 `?iter=` 或放大观察即可确认。

## 精度：为什么是扰动法

GPU 编译器会把经典的 two-sum 误差项 `(a-(s-v))+(b-v)` 代数消成 0，于是 GPU 上的 double-float 模拟会静默退化成 f32——半高低于 `1e-7` 时画面会碎成量化方块。

因此这里用**扰动法（perturbation）**：

1. CPU 用 f64 在视野内挑一个**落在集合里**的点，走一条参考轨道 `R_n`，写入 storage buffer。
2. GPU 只迭代小量 `Z ≈ z - R`，每步 `Z ← 2·R·Z + Z² + dc`。
3. `dc` 是像素相对参考点的偏移，量级等于视野半高；`Z` 也是，所以 f32 对 `Z` 足够。

结果是半高到 `1e-9` 仍能看到丝状结构（偶发 glitch 是扰动法的已知现象，继续深潜需要 rebasing）。

**迭代预算必须跟着深度走。** 逃逸时间随深度增长，原来那条曲线在 `h < 4.6e-5` 就封顶在 700，深潜时几乎每个像素都被判成"内部"，整屏发黑——正好是这个渲染器存在的意义所在的那段缩放范围。现在按 `180 + 135·log10(1.45/h)` 算，封顶 2000。到 `1e-12` 需要 2000 以上，已经超出上限了。

**同一个着色器也要遵守**：`fwidth(mu)` 要求 `mu` 在一致控制流里写入。若写成 `if (escaped) { mu = … }`，导数未定义会变成 NaN，整屏发黑。

### 深潜时变成方块

`dc = local + refOffset` 里，`refOffset`（视图中心相对参考点的偏移）是**通过 f32 uniform 传过去的**。f32 在 `x` 处的量化步长是 `x·1.2e-7`，换算成屏幕像素就是

```
块宽 ≈ (refOffset / h) · 6e-8 · H
```

所以 `refOffset` 相对视野半高 `h` 一变大，整屏就会按这个步长量化成方块——不是渲染停了，是每个像素的输入变成同一个值了。

真正让它变糟的是**重建判据只看"视图中心漂移"**。在正中心滚轮放大时中心几乎不动，漂移永远小于 `0.25h`，于是参考点一直停在几万倍之前的缩放上：`refOffset` 冻结、`h` 一路缩小，比值失控。实测能到 `off/h ≈ 4.5e6`，也就是 151 像素见方的色块。

现在重建条件是四条任一成立：

- 需要更长的轨道（`iter` 涨了）；
- 中心漂移超过 `0.25h`（平移）；
- `|refOffset| > 8h`（offset 相对视野太大，会开始量化）；
- 缩放变化超过 2 倍（原地放大时只有这一条会触发）。

另外"参考点 = 原点"的兜底只允许在 `h ≥ 1e-4` 时使用：再深一点，`dc` 就等于绝对坐标（~0.75），f32 只能分辨到 `6e-8`，深于这个尺度必然是方块。更深的视图如果网格里一个存活点都没有，就退而取"活得最久"的那个采样点——它至少还在视野附近，偏移量能分辨。

## 幂次 d：同一台机器上的公式族

`z^d + c` 的幂次是一个滑块（2–8），不是十个独立页面。理由很实际：参考轨道、漂移判据、交互降分辨率、自动迭代这一整套三百多行只该有一份；而"族"有意思的地方恰恰是**同一个坐标在不同 d 下长什么样**，分开就没法对照。

**关键在系数，不在迭代。** 扰动展开是

```
Z_{n+1} = Σ_{k=1..d} C(d,k)·R_n^(d-k)·Z_n^k + dc
```

每一个 `C(d,k)·R^(d-k)` 都只是 `R` 的函数。所以 CPU 在建参考轨道时顺手把 d−1 张系数表一起算好（f64），按块写进 storage buffer；GPU 用 Horner 形式

```
Z ← Z·(D₁ + Z·(D₂ + Z·(… + Z))) + dc
```

每步只多 d−1 次复数乘法，跟"把复数取 d 次幂"是同一量级，和 `d` 的关系是线性的而不是幂次的。`d = 2` 保留原来那段算式逐字不变，输出不受影响。

**不能只留前两阶。** 这是最先试的写法（`d·R^(d−1)·Z + C(d,2)·R^(d−2)·Z²`），代价最省，但近边界处 `|Z|` 会爬到和 `|R|` 同量级，三阶项不再可忽略。实测 `d = 3` 在半高 `2e-6`（才 ×7×10⁵ 的缩放）时平滑逃逸时间就差 2.2，肉眼可见的错色。改成完整阶之后，同一位置与原式 f64 逐点迭代的差是 0。

**两个必须记着的退化情形：**

- 参考点正好在原点时 `R ≡ 0`，所有系数都是 0，`Z` 直接退化成 `dc`——`d = 2` 恰好等价于普通迭代，`d > 2` 就是整屏发黑。所以"参考点在原点"必须走直接迭代那条路（`Z ← Z^d + dc`），不能交给级数。
- 逃逸半径仍取 `|z| > 16`（`mag > 256`）：只要 `|z| > 16` 且 `|c|` 有界，`|z|^d ≥ |z|² > |z| + |c|`，对任何 `d ≥ 2` 都发散。平滑上色的归一化常数跟着换成 `log d`，`d = 2` 时它正好等于原来的 `log 2`。

代价是清楚摆着的：`d = 8` 的每步是 `d = 2` 的七倍复数乘法，深缩时会掉帧；两侧的预设坐标（海马谷、大象谷…）是 `d = 2` 的地标，换 `d` 之后去那里多半只能看到一片内部。
